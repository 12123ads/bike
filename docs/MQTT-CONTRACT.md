## 1. 架构变更：broker 跑在服务端进程里

**【定】不再用 `/opt/mqtt` 的 Mosquitto，改用 `amqtt` 嵌进 Python 服务端同一个进程。**

理由是你的规模：**一辆车**。原方案里 broker 独立的价值全部来自多设备隔离，
而单设备下那些价值不存在：

| 原方案要做的事 | 单车 + 内置 broker 之后 |
| --- | --- |
| 改 `/opt/mqtt/config/mosquitto.conf` 加 `acl_file`，**重启在跑的服务**（§11 #4） | **不需要动 Mosquitto**，那个需要你批准的操作没有了 |
| 设计 ACL 规则形态、设备账号命名与配发（§11 #5） | 一个账号、一条前缀规则，写死在代码里 |
| 「任何一台设备被撬开就能读全部车辆位置」 | 只有一台设备，它读到的就是它自己的 |
| broker 加 8883 listener + 证书挂载卷 | listener 由服务端自己建，证书路径在服务端配置里 |
| 进程间多一跳 TCP | 上行报文在进程内直接进 ingest，少一次序列化 |

⚠ **顺带核实到的事实**：`/opt/mqtt` 的 Mosquitto **当前根本没在运行**——
没有容器（`docker ps -a` 里无 mosquitto）、1883/9001 无监听，日志最后一行是
`1788105895: mosquitto version 2.0.22 terminating`。所以「动在跑的服务」这个风险本来也不存在，
但内置 broker 依然是对的选择，理由是上面那张表而不是这一条。

代价，写清楚：

- **broker 和业务逻辑同生共死。** 服务端崩了 broker 也没了，设备连不上。
  单车场景可接受（反正服务端挂了也没人处理报文），多车场景要拆回去。
- **`amqtt` 是纯 Python broker，不是 Mosquitto 的性能级别。** 单车每 5~30 分钟几条报文，
  差着好几个数量级，不构成问题。
- **HA 在另一台机器上**（§9.4），所以内置 broker **仍然要对外开监听端口**，
  这一点和外置 broker 没区别。

## 2. 认证与传输安全

**【定】设备侧改成「TLS + 用户名口令」，不再要求双向 TLS。**

DESIGN.md §8.2/§9.2 写的是「设备 → broker 无条件双向 TLS」。单车场景下这条**降级是等价的**，
理由：mTLS 相对口令的唯一优势是「私钥不出设备」，但**本方案的设备就装在车上，
拆开就能读 flash**（§5.4 第 1 条已经承认了这个攻击面）。
客户端证书和口令一样都在那块 flash 里，攻击者拆开设备两者都能拿到。
所以 mTLS 在这里买不到额外安全，只买来 §11 #24 那个「产线私钥怎么灌」的难题。

**因此 §11 #24 一并作废**，不是被解决，是前提没了。

- 上行/下行**一律走 TLS**（`ssl: true` 的 listener），端口默认 **8883**。
  证书由 `ebike_server.certs` 生成自签 CA + 服务端证书，或换成你自己的。
- 设备用**用户名 = 设备 id、口令 = 32 字节随机串**，服务端用 argon2 校验
  （`amqtt` 的 `FileAuthPlugin` + `pwdlib`）。
- **仍然支持 mTLS**：配置 `auth.mode = "cert"` 就切到 `UserAuthCertPlugin`，
  按证书 SAN 里的 `spiffe://<domain>/device/<id>` 认身份。想要就打开。

⚠ **一个必须知道的 `amqtt` 行为**：它的 listener 建 SSLContext 时写死
`ssl_context.verify_mode = ssl.CERT_OPTIONAL`（`amqtt/broker.py:317`，本机读的源码）。
意思是**TLS 层不强制客户端出证书**，身份是在认证插件里判的。
所以 `cert` 模式下「没带证书的客户端」能完成 TLS 握手、然后在 CONNECT 阶段被拒——
拒绝点比 Mosquitto 的 `require_certificate true` 晚一层。单车场景无实质影响，但别以为是 TLS 层挡的。

## 3. ACL

一条规则，写在服务端配置里，不是文件：

| 账号 | 可发布 | 可订阅 |
| --- | --- | --- |
| `bike01`（设备） | `ebike/v1/bike01/up/#` **和 `ebike/v1/bike01/lwt`** | `ebike/v1/bike01/dn/#` |
| `ha`（Home Assistant） | 无 | `ebike/v1/+/state` |
| `svc`（保留名） | 全部 | 全部 |

设备**不能**发布 `state`，也**不能**订阅自己的 `up/`——防的是设备被撬开后
伪造「一切正常」的状态覆盖服务端判断。
HA **只能**订阅 `state`，看不到原始报文，这就是 §9.4「跟 HA 解耦」的落地。

`lwt` 的发布权是**必需**的，不是疏漏：§4.2 要求固件主动断开前发 `{"lwt":0}`，
那条报文的 topic 是 `ebike/v1/<id>/lwt`，不在 `up/#` 下面。

⚠ **`svc` 是保留名，当前并不存在**：ACL 里有它的条目，`Service.ingest` 也认它，
但 `ebike-server init` **从不给它建口令**（`__main__.py` 只给设备和 `ha` 建）。
服务端自己发布走的是 `broker.internal_message_broadcast()`，即以 broker 身份发，
不占一个 MQTT 客户端连接，所以不需要账号。留着这个条目是为了将来真要开
一个外部服务账号时不用改 ACL 形状。

⚠ `amqtt` 的 `TopicAccessControlListPlugin` 有个坑（`amqtt/plugins/topic_checking.py:69-71`）：
**`publish-acl` 没配的时候，发布一律放行**（为了兼容 hbmqtt）。
所以 `publish-acl` 必须显式配，漏配是静默放开而不是报错。
服务端启动时断言的是**每个已配置设备都有 publish 条目**——
~~断言它非空~~ 那样写恒为真（`build_acl` 里已经先塞了 `svc` 键），
等于没有保险。`tests/test_certs.py::test_publish_acl_assertion_covers_every_device`
钉住了这一点。

## 4. Topic 树

`<id>` = 设备 id，`[a-z0-9-]{1,32}`，出厂烧录。单车下就是 `bike01`，但**仍然留在 topic 层级里**，
这样将来加第二辆车不用改契约。

| topic | 方向 | QoS | retain | 谁发 |
| --- | --- | --- | --- | --- |
| `ebike/v1/<id>/up/hello` | 上行 | 1 | 否 | 设备，每次连上后的第一条 |
| `ebike/v1/<id>/up/loc` | 上行 | 1 | 否 | 设备，位置点（单点或批量） |
| `ebike/v1/<id>/up/tele` | 上行 | 1 | 否 | 设备，遥测 |
| `ebike/v1/<id>/up/event` | 上行 | 1 | 否 | 设备，事件/告警 |
| `ebike/v1/<id>/up/ack` | 上行 | 1 | 否 | 设备，确认一条下行 |
| `ebike/v1/<id>/lwt` | 上行 | 1 | 见下 | **broker 代发**遗嘱；固件也会主动发一条覆盖 |
| `ebike/v1/<id>/dn/cmd` | 下行 | 1 | **否** | 服务端，指令 |
| `ebike/v1/<id>/dn/secret` | 下行 | 1 | **否** | 服务端，per-user 密钥 |
| `ebike/v1/<id>/state` | 派生 | 1 | **是** | **服务端**（设备从不发这个） |

最长 topic = `ebike/v1/` + 32 + `/up/hello` = **50 字节**，远在 256 以内（§8.2）。

**`lwt` 的 retain 分两种情况**，这是实现事实，不是设计选择：

- **broker 代发的遗嘱**：retain 位由设备 CONNECT 时的 `will_retain` 决定，
  固件在 `AT+MCONFIG` 里配（`modem.c`）。
- **固件主动发的 `{"lwt":0}`**：走普通 publish，`AT+MPUBEX` 的 retain 参数
  **硬编码 0**（契约 §4.1 要求上行/下行都不 retain），所以它 **retain=false**，
  覆盖不了 broker 侧那条 retain 的 `{"lwt":1}`。

**端到端行为仍然正确**，因为服务端的 `_on_lwt` 是「收到消息就更新 DB 字段」，
**不依赖 retain**（`service.py`）。所以 §4.2 那句「先发 `{"lwt":0}` 覆盖掉它」
要理解成「让服务端知道这次是优雅下线」，而不是「覆盖 broker 的 retain 表」。

### 4.1 为什么下行 **不能** retain

§11 #25 问的是「模组关机期间下行怎么排队」。答案：**服务端自己排，不靠 broker retain。**

retain 每个 topic **只留最后一条**。如果 `dn/secret` 用 retain，
连着轮换两把密钥、设备中间没上线，第一把就永久丢了——而它可能是唯一还能开锁的那把。
`dn/cmd` 同理，两条「去定位」会塌成一条。

所以：**下行全部 `retain=False`，服务端把未确认的下行存在 SQLite 的 `pending_downlink` 表里**，
在设备连上（`up/hello` 或 broker 的 `CLIENT_CONNECTED` 事件）时按 `id` 顺序发，收到 `up/ack` 才删。
**这决定了 secret 轮换的最坏时延 = 一个上报周期**（省电档 5~30 分钟，§4）。

`dn/agps` 是唯一的例外候选（星历天然只要最新一份），但**本版不实现 AGPS**，
所以 topic 树里没有它——等 R7 真做 AGPS 时再加，届时它可以 retain。

### 4.3 ⚠ amqtt 的 retain 会漏给任何连上来的客户端

**这是实测确认的 `amqtt` 0.12.0 行为，不是设计。** 客户端一连上，broker 就遍历
**全局**订阅过滤器表，把匹配的 retain 消息推给这个新会话——不管它自己订了什么：

```python
for topic in self._subscriptions:                 # amqtt/broker.py:601（0.12.0 实测）
    await self._publish_retained_messages_for_subscription((topic, QOS_0), client_session)
```

而 `_publish_retained_messages_for_subscription`（`broker.py:1134`）**完全不调
`_topic_filtering`**——订阅 ACL 和接收 ACL 在这条路径上都不生效。

实测：HA 订过 `ebike/v1/+/state` 之后，设备（只订 `dn/#`）一连上就收到了那条
retain 的 state。`tests/test_e2e.py::test_retained_state_leaks_to_device_on_connect`
把这个行为钉住了。

**当前不构成危害**：唯一 retain 的是 `state`，内容就是设备自己刚报的位置；
单车场景只有一个设备账号。**§4.1 那个「下行绝不 retain」的决定在这里额外挡住了
最坏情况**——如果密钥下发用了 retain，这条路径会把密钥推给任何连上来的客户端。

**加第二辆车之前必须解决**：`ebike/v1/+/state` 匹配所有车，bike02 一连上就会
收到 bike01 的位置。两条路：让 HA 改成每车一条精确订阅（不用通配符），
或者换回 Mosquitto。

### 4.2 为什么「离线」**不能**靠 LWT 判定

这条是本轮发现的、原方案会直接踩坑的地方。

§8.4 的默认档是**模组关机 / PSM+**。也就是说：**设备正常工作时，每个周期都会非优雅断连一次。**
LWT 的语义是「非优雅断连就发」，所以 LWT 会在**每个正常周期**触发。
如果 HA 拿 LWT 当在线判据，那这辆车 99% 的时间显示「离线」——而它是好的。

**【定】判据：**

- **`online` 由服务端超时算**：`now - last_seen > offline_after`，
  `offline_after` 默认 `3 × report_interval + 120 s`，随上报周期联动。
  **`interval` 指令改过周期后阈值会跟着走**：设备 ack 成功时服务端回写
  `DeviceConfig.report_interval` 并落库（`service.py` 的 `_apply_acked_cmd`），
  重启后从 `meta` 表恢复。不跟的话把周期调大会让健康的车被判离线。
- **LWT 仍然保留**，payload 是 `{"lwt":1}`。它的用途**不是**判离线，
  而是给「设备是否是优雅下线」留一条痕迹：固件主动断开前会先发一条
  `{"lwt":0}`，服务端收到就把标记清掉（**靠收消息，不靠 retain 覆盖**，
  见 §4 那段说明）。**`lwt=1` 且超时 = 可能真出事了**（掉电/剪线/信号丢失）。
- 因为**没有备份电池**（§6），剪线的瞬间设备来不及说任何话，
  所以 `lwt=1` 也只是「非优雅」，**区分不了「正常关机档」和「被剪线」**。
  这不是契约的缺陷，是「不装备份电池」这个取舍的直接后果（§6 表格第一行）。

## 5. 报文格式

JSON，UTF-8，**紧凑无空格**。字段名一律缩到 1~4 字母——理由是 §1 那条算术：
`AT+MQTTMODE=1` 的 HEX 模式让串口字节数翻倍，9600 baud 下 1 字节 payload ≈ 2 个字符 ≈ 2 ms。
**省 100 字节 = 省 0.2 秒的模组开机时间。**

所有报文共有的两个字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `t` | int | 设备侧 Unix 秒。**可能是错的**——见 §5.6 |
| `q` | int | 设备侧单调递增序号，掉电不清零（存 NVS）。服务端用它去重 |

### 5.1 `up/hello`

```json
{"t":1788105895,"q":41,"fw":"0.1.0","boot":3,"rst":"pin","kid":7}
```

| 字段 | 含义 |
| --- | --- |
| `fw` | 固件版本 |
| `boot` | 累计启动次数（NVS） |
| `rst` | 复位原因：`por`/`pin`/`wdt`/`soft`/`off`（System OFF 唤醒） |
| `kid` | 设备当前持有的密钥集版本号。**服务端用它判断要不要补发 secret** |

### 5.2 `up/loc`

单点：

```json
{"t":1788105895,"q":42,"s":"g","la":31.230416,"lo":121.473701,"a":8.0,"sp":0.0,"hd":0,"n":9}
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `s` | str | 定位源：**`"g"` = GNSS，`"l"` = 基站(LBS)**。对应 §9.5 的 `src=lbs` |
| `la` `lo` | float | WGS84 纬度/经度，**保留 6 位小数**（≈0.11 m，再多是噪声） |
| `a` | float | 水平精度圈半径，米。**GNSS 与 LBS 同字段**，LBS 会是几百到几千 |
| `sp` | float | 速度 m/s，可省 |
| `hd` | int | 航向度 0~359，可省 |
| `n` | int | 卫星数，`s="l"` 时省略 |

批量（断网补发，见 §9.1 那个待决项）：**payload 是一个 JSON 数组**，元素同上。

```json
[{"t":1788105895,"q":42,...},{"t":1788106195,"q":43,...}]
```

**批量上限【定】= 20 点**。算术：单点紧凑 JSON ≈ 95 B，20 点 + 数组开销 ≈ 1.95 KB，
HEX 后 3.9 KB，**卡在 4100 B 上限内且留了 5% 余量**（§8.2）。
20 点在省电档（5~30 分钟一报）= 100 分钟到 10 小时的补发窗口。
服务端**硬拒**超过 20 点的数组，不是截断——静默截断会让丢点看起来像没丢。

### 5.3 `up/tele`

```json
{"t":1788105895,"q":44,"up":86400,"v":54.2,"csq":18,"tmp":21}
```

`v` = 电池电压（V，1 位小数，来自 §3.6 的门控分压）；`csq` = `AT+CSQ` 的 rssi 档；
`up` = 本次开机运行秒数；`tmp` = 芯片温度。

**`v`、`csq`、`tmp` 都可省**，只有 `t` `q` `up` 恒在。

⚠ **缺省必须是「字段不出现」，不是发 0**（审计 M8）。ADC 读失败时旧固件发
`"v":0.0`，服务端把它当真值落库、`volt_to_pct` 插到曲线最低点，HA 上显示
0 V / 0 %——看起来像被剪线，而没人知道那是假数据。固件靠 `has_volt`
决定发不发（`tmp` 同理靠 `has_temp`）。真读到 0 V（线断了）**照发** ——
「缺省」和「真的是 0」是两件事。

服务端侧对应：`tele` 表的 `volt` 列为 NULL，`state` 里 `v`/`pct` 两个键整个缺席（§7）。

### 5.4 `up/event`

```json
{"t":1788105895,"q":45,"e":"motion","d":{"mg":180}}
```

`e` 的取值是**闭集**，服务端拒绝未知值：

| `e` | 何时 | `d` |
| --- | --- | --- |
| `boot` | 上电/唤醒 | — |
| `motion` | LIS2DW12 `SENSOR_TRIG_MOTION`（§3.7） | `{"mg":<触发幅度>}` |
| `still` | 软件静止计时超时（`CONFIG_EBIKE_STILL_AFTER_S`；硬件 `SENSOR_TRIG_STATIONARY` 走 INT2，本板没接线） | — |
| `unlock_ok` | §5.2 三重校验全过 | `{"uid":<user_id>}`。远程开锁（§6.1）报 `uid:0` |
| `unlock_deny` | 回了 `69 82` | `{"uid":<user_id>}`。**不含失败原因**——§5.2 说了不给攻击者区分信道，上行也不给。uid 未知时固件报 `0`（**不是 null**：`%u` 没有 null 形式） |
| `lock_state` | 锁位置反馈开关变化 | `{"locked":true/false}` |
| `lowbatt` | 跨过 §6 的**任一**阈值 | `{"lv":1\|2\|3,"v":48.1}`。**含 lv=3**（进 System OFF 前那一级也报） |
| `ble_err` | BLE / GATT 层异常 | `{"c":<码>}`（Zephyr 负 errno） |

**`d` 的键与值也是闭集，服务端逐个校验**（`contract.py` 的
`_EVENT_DETAIL_SPEC`）：未知键、类型不对、越界一律**拒收整条报文**。

| 键 | 类型 | 范围 |
| --- | --- | --- |
| `mg` | int | 0 ~ 16000 |
| `uid` | int | 0 ~ 2³²−1 |
| `lv` | int | 0 ~ 3 |
| `v` | float | 0 ~ 70（同 §5.3 的 `v`） |
| `locked` | bool | `true` / `false`（**不接受 0/1**） |
| `c` | int | int32 范围 |

⚠ 这条校验是 2026-09-03 审计（M4）补的。此前只校验「`d` 是对象」，
值可以是任意 JSON —— 一个字符串型 `mg` 会一路存进库、再被网页事件面板
拼进 `innerHTML`，构成存储型 XSS（配合会话 cookie 可调 `/api/cmd`）。
网页侧的转义是第二道墙（`web_assets.py` 的 `esc()`），两道都在。

### 5.5 `up/ack`

```json
{"t":1788105895,"q":46,"id":"c-17","ok":1}
```

失败：`{"t":...,"q":47,"id":"s-3","ok":0,"er":"badmac"}`。
`id` 必须逐字回抄下行的 `id`。服务端收到才把 `pending_downlink` 里那条删掉（§4.1）。

### 5.6 时间戳为什么不可信

设备**没有 RTC 电池**，掉电后时间从 0 开始。它靠 `+NITZ:` URC 拿运营商时间（§8.1，免费无往返，
`AT+CTZU`/`AT+CTZR` 缺省都已开），开机时另外主动查一次 `AT+CCLK?` 兜底，
但**模组关机档下，每次开机到拿到时间之间的报文 `t` 是错的**。

**【定】服务端两个时间都存**：`t_dev`（设备说的）和 `t_srv`（服务端收到的）。
**落库、排序、HA 展示一律用 `t_srv`**；`t_dev` 只用来诊断和算批量补发的相对间隔。
设备侧在还没拿到 NITZ 时把 `t` 填 **0**，明确表示「我不知道现在几点」。

## 6. 下行报文

**下行有一个独立的、比上行小得多的大小上限【定】= 256 B**
（`contract.MAX_DOWNLINK_BYTES` / 固件 `PROTO_MAX_DN_PAYLOAD`）。

理由和上行的 4100 B 完全不同：下行到达设备时是**一整行** AT URC ——
`+MSUB: "<topic>",<len>,"<hex payload>"`，而 HEX 模式让 payload 字节数翻倍。
能收多大的下行由固件的**行缓冲**（`modem.c` 的 `LINE_MAX = 640`）决定，
不是由模组单包上限决定：

```
可收 payload = (LINE_MAX-1 − 框架) / 2
框架 = '+MSUB: ""' + topic(≤51) + ',<len>,' + 两个引号 ≈ 39 + (51−22)
256 × 2 + 68 = 580 ≤ 639   ✓（余量 59）
```

⚠ 超限的下行在设备侧被**整条丢弃**（`read_line` 返回 `-EMSGSIZE` 并 LOG_ERR）。

这条路径以前是**静默截断**，而截断的实际归宿比「收到一个错值」更隐蔽：
那一刀必然砍掉 payload 的结束引号（HEX 区里只有 `0-9A-F`，不可能再出现一个
字面量 `"`），于是固件的 `handle_msub` 走「找不到结束引号」分支——
**当作已消化、一条日志都不打**。症状是「下行凭空消失，而服务端每次设备上线
都重发同一条」，运维侧看到的只有 `/pending` 里 tries 一直涨。

更早的矛盾在数字本身：`LINE_MAX=512` 只能收 236 B 下行，而 `dn_payload`
按 3900 B 开——**声称能收 3900，实际 237 B 就开始丢**，差 16 倍。

现在两端都硬拒且都有日志：服务端构造时 400（`/cmd`、`/secret` 立刻报错），
设备收到时丢整行并 LOG_ERR。最长的实际下行是 `dn/secret`（实测 90 B），
离 256 有充裕余量。

### 6.1 `dn/cmd`

```json
{"id":"c-17","c":"locate"}
```

| `c` | 含义 | `a`（参数） |
| --- | --- | --- |
| `ping` | 要一条 `up/tele` | — |
| `locate` | 立刻定位并上报 | `{"to":60}` 最长等待秒数 |
| `unlock` | 远程开锁 | — |
| `lock` | 远程上锁 | — |
| `interval` | 改上报周期 | `{"s":900}` |
| `tier` | 切功耗档（§8.4） | `{"m":"off"或"pro"}` |
| `reboot` | 重启主控 | — |

⚠ **`unlock` 的安全前提**：远程开锁**绕过了 §5.2 的挑战应答**——它信的是 MQTT 那一层的 TLS + 口令。
这条命令的实际含义是「谁能登进服务端谁就能开你的车」。
**默认在服务端配置里关闭**（`allow_remote_unlock = false`），要用自己打开。
本地手机 BLE 开锁不受影响，它完全离线（§5.2）。

### 6.2 `dn/secret`

```json
{"id":"s-3","op":"set","uid":1,"kid":8,"k":"<base64 32 字节>"}
```

`op` = `set` / `del` / `wipe`。`kid` 是密钥集版本，设备存进 NVS 并在 `up/hello` 里回报（§5.1），
服务端据此判断要不要补发。`k` 是 §5.2 那个 HMAC-SHA256 的 secret，**base64 的 32 字节**。

**字段是强校验的，不是「约定」**（`contract.build_secret`）：`k` 必须是合法
base64 且解码后**恰好 32 字节**，`uid` 是 uint32、`kid` 是 uint16。
越界或长度不对的一律在构造时 `ContractError` → `/secret` 回 400。

⚠ 这条校验是必需的而不是防御性的：固件 `proto_dec_secret` 强校验
`olen == SECRET_LEN`，一条 4 字节的 `k` 会被设备 ack 成 `badfmt`，
而服务端的重发逻辑会**一直重发同一条坏报文**——每轮唤醒都白花一次射频。
校验放在入队前，坏报文进不了队列。

⚠ **这条报文里有明文密钥材料。** 它的保护完全依赖 §2 的 TLS。
`retain=False` 是硬要求（§4.1），否则密钥会留在 broker 的 retain 表里。
服务端日志**不打印 `k` 字段**，`contract.py` 里有一个专门的脱敏路径。

**§11 #13「离线首次配对」本文不解决**——设备从没上过 4G 时第一把密钥怎么进去，
仍然是待决项。当前实现假设：**第一把密钥用 SWD/UF2 随固件一起烧进去**。

## 7. `state`：服务端派生，HA 唯一订阅的东西

```json
{"t":1788105895,"on":true,"mo":"parked","la":31.230416,"lo":121.473701,
 "gla":31.228405,"glo":121.478066,"a":8.0,"s":"g",
 "v":54.2,"pct":78,"gf":"in","ls":1788105895,"lwt":0,"lk":true,"fw":"0.1.0"}
```

⚠ **键集是可变的，不是固定 16 个。** 服务端只在有数据时才放对应的键：

- 还没收到任何位置点 → **`la` `lo` `gla` `glo` `a` `s` 六个键整个缺席**（不是 null）
- 还没收到任何遥测 → **`v` `pct` 缺席**
- 其余 8 个键（`t` `on` `mo` `ls` `lwt` `lk` `gf` `fw`）**总是在**

HA 侧因此一律用 `.get()` 取值，不做 `KeyError` 假设。

| 字段 | 含义 |
| --- | --- |
| `on` | 在线。**服务端超时算的，不是 LWT**（§4.2） |
| `mo` | `moving` / `parked`。由 `up/event` 的 `motion`/`still` + 位移共同判 |
| `la` `lo` | WGS84，原样透传 |
| `gla` `glo` | **GCJ-02**，服务端转换后**新增的字段，不覆盖原字段** |
| `a` | 精度圈半径，透传给 HA 实体属性——这就是「误差圈可见」的验收（§9.4） |
| `pct` | 电量百分比，48V 铅酸/锂电的电压-电量曲线在服务端配置里 |
| `gf` | `in` / `out` / `null`（未配围栏） |
| `ls` | `last_seen`，服务端时钟 |
| `lwt` | 最后一次断连是否非优雅（§4.2） |
| `lk` | 锁是否锁着，来自 `lock_state` 事件。**`null` 是常态**——位置反馈微动开关是选配的，没接就永远拿不到。HA 侧必须能显示「未知」，**不能把 null 当成「没锁」** |
| `fw` | 固件版本，来自 `up/hello` 的 `fw`（§5.1）。`null` = 还没收到过 hello。HA 用它填设备卡片的「固件版本」 |

**`retain=true`** —— 这就是「重启 HA 立即有位置」那条验收成立的全部原因（§9.4）。

**坐标转换目标系【定】= GCJ-02**，因为国内地图底图（高德/腾讯）都是 GCJ-02，
HA 默认底图是 OSM（WGS84）。**两套都发，让 HA 侧自己选**——
覆盖原字段会让「换个底图」变成改服务端。BD-09 不做，需要时在 HA 侧转。
